# Tell, Don't Ask

Tell, Don't Ask — принцип проектирования: не спрашивай у объекта
данные, чтобы принять решение снаружи, — скажи объекту, что делать.
Логика должна жить там, где живут данные. Если клиент делает
`if (obj.getX() > 0) obj.setY(...)` — это нарушение: решение
принимается снаружи, хотя данные — внутри.

## Файлы

- `tell_dont_ask.hpp` — `bad::Account` + свободная `withdraw()`
  (клиент спрашивает баланс и сам решает) и `good::Account` с
  методом `withdraw()` (объект сам проверяет инвариант). Второй
  пример: `bad2::User` с `isActive()` и `good2::User` с
  `sendEmail()`, который сам проверяет активность.
- `test.cpp` — проверяет, что «плохая» версия работает через
  геттеры/сеттеры, а «хорошая» — через методы объекта; что
  `good::Account` отвергает отрицательные суммы и что
  `good2::User` бросает при неактивном пользователе.

## Ключевые идеи

1. **Логика — там, где данные.**
   В `bad::withdraw` логика снятия живёт **вне** `Account`, хотя
   данные (`balance_`) — **внутри**. В `good::Account::withdraw`
   логика и данные вместе.

2. **Объект сам проверяет инвариант.**
   `good::Account::withdraw` проверяет `amount <= 0` и
   `amount > balance_`. Клиент не может случайно нарушить
   инвариант, потому что не имеет доступа к `balance_` напрямую.

3. **Клиент не знает про внутренние условия.**
   В `bad2` клиент знает про `isActive()` и сам решает, отправлять
   ли письмо. В `good2` клиент просто вызывает `sendEmail()`, а
   объект сам решает. Добавление нового условия (например,
   «не заблокирован») не ломает клиентов.

4. **Геттеры остаются — но не для принятия решений.**
   `balance()` в `good::Account` — query для чтения (показать,
   логировать). Но клиент не может на его основе менять состояние:
   `withdraw()` сам решает, можно ли снять.

5. **Исключения вместо «тихих» проверок.**
   `good::Account::withdraw` бросает `std::runtime_error` при
   недостатке средств и `std::invalid_argument` при
   отрицательной сумме. Клиент не может «забыть» проверить
   условие — объект сам сообщит об ошибке.

## Ограничения

1. **Tell, Don't Ask — не запрет геттеров.**
   Геттеры нужны для отображения, логирования, сериализации.
   Принцип про **принятие решений**: `if (obj.getX() > 0)
   obj.setY(...)` — нарушение; `std::cout << obj.getX()` — норма.

2. **Не всегда применим к «тупым» структурам данных.**
   `struct Point { int x, y; }` — это DTO, у него нет инвариантов,
   и клиент может свободно читать/писать поля. Tell, Don't Ask
   про объекты с **поведением** и **инвариантами**, а не про
   контейнеры данных.

3. **Может привести к «божественным объектам».**
   Если следовать принципу буквально, вся логика стягивается в
   объект. Нужен баланс: объект владеет **своими** инвариантами,
   но не логикой всего приложения.
