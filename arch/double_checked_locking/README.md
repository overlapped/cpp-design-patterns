# Double-Checked Locking (DCLP)

## Назначение
Паттерн **Double-Checked Locking (DCLP)** оптимизирует ленивую потокобезопасную инициализацию (lazy initialization). Он позволяет избежать захвата дорогостоящего мьютекса при каждом обращении к уже созданному объекту: блокировка берётся **только один раз** — в момент непосредственного создания экземпляра.

## Почему «наивный» DCLP в C++ сломан (UB)
До C++11 (или при использовании обычного «сырого» указателя `T* instance_ = nullptr;` без `std::atomic`) паттерн приводил к **Undefined Behavior** по двум причинам:
1. **Гонка данных (Data Race)**: один поток пишет в `instance_` под мьютексом, а другой читает `instance_` без мьютекса — в модели памяти C++ это UB.
2. **Переупорядочивание инструкций (Instruction Reordering)**: выражение `instance_ = new T()` компилятор и процессор могут разбить на три шага:
   * Выделить память (`ptr = operator new(sizeof(T))`);
   * Записать адрес в `instance_` (`instance_ = ptr`);
   * Вызвать конструктор `T` в выделенной памяти.
   Другой поток на первой проверке увидит `instance_ != nullptr` и начнёт читать поля ещё **не сконструированного** объекта.

## Как это решается в C++11+ (`acquire` / `release`)
* **`instance_.store(ptr, std::memory_order_release)`**: запрещает компилятору и процессору переносить операции записи (инициализацию полей объекта `T`), выполненные *до* `store`, в область *после* `store`.
* **`instance_.load(std::memory_order_acquire)`**: гарантирует, что если поток прочитал ненулевой указатель, он увидит все записи в память, сделанные потоком-создателем до `release`.
* **Вторая проверка (`std::memory_order_relaxed`)**: выполняется уже под защитой `std::mutex`, который сам по себе обеспечивает синхронизацию памяти между потоками, входившими в критическую секцию.
* **Безопасность исключений**: объект сначала создаётся во временный `std::unique_ptr<T>`, и только после успешного завершения конструктора указатель публикуется в `instance_`. Если конструктор бросит исключение, память не утечёт, а `instance_` останется `nullptr`.

## Альтернативы в стандартном C++
В современном продакшн-коде ручной DCLP обычно заменяют более лаконичными и менее подверженными ошибкам средствами стандартной библиотеки:
1. **Magic Statics (C++11)**: локальная `static`-переменная внутри функции (`static T instance;`) гарантированно инициализируется потокобезопасно один раз. Подходит для синглтонов, но не для полей экземпляра класса.
2. **`std::call_once` + `std::once_flag`**: стандартный способ ленивой инициализации полей класса (также показан в `LazyCallOnce` в этом файле).

## Сравнение подходов

| Подход | Область применения | Сложность / Риск ошибок |
| :--- | :--- | :--- |
| `static T instance` (Meyers) | Глобальный / статический синглтон | Минимальная |
| `std::call_once` | Поле экземпляра класса | Низкая |
| `LazyDclp` (`std::atomic` + `mutex`) | Поле экземпляра, учебный разбор модели памяти | Высокая (требует строгих барьеров `acquire`/`release`) |
